# Brainstorm gate — לפני בנייה

מקור דפוס: [obra/superpowers `brainstorming`](https://github.com/obra/superpowers/tree/main/skills/brainstorming) (+ `writing-plans`).  
רתמה: `vfharness` · מחליטים: `vfmakers/crews/decide.md` · גריל פנייה: `vfconvert/hq/GRILL.md`.

## חוק ברזל

אין ליישם (קוד, פק חדש, שינוי צינור, HTML בריף, סקיל חדש) לפני:

1. סיווג המסלול בקול,
2. הצגת כוונה / עיצוב קצר,
3. אישור שותף אנושי (בעלים / ראש צוות) — גם למשימות «פשוטות».

## שלושה מסלולים

הכרז את הסיווג לפני השאלה הראשונה:

| מסלול | מתי | תוצר לפני אישור |
|---|---|---|
| **Spike** | «אפשר?» / בדיקת היתכנות זולה | 2–3 משפטים + מה ינוסה; קוד זמני מסומן throwaway |
| **Bounded** | שינוי בזרימה **שכבר קיימת** בריפו (דגל, פלייבוק אחד, תיקון סנסור) | עיצוב קצר **בצ׳אט** (כמה משפטים) — בלי קובץ spec |
| **Architectural** | פק/מודול חדש, שינוי ממשק בין פקים, צינור, חוקה | שאלות → חלופות → עיצוב מחולק → spec קצר → אחר כך תוכנית משימות |

בספק — קח את הכבד יותר. מורכבות שהתגלתה באמצע → עצור, הכרז שדרוג מסלול. אין הורדה באמצע.

## Checklist (סדר)

1. הקשר — קרא פק/פלייבוק רלוונטי (`skill-first.md`).
2. שאלות מבהירות — רק העמוסות; אל תמציא ₪ / Insights.
3. 2–3 גישות + המלצה אחת.
4. הצג עיצוב / כוונה → **עצור**.
5. אחרי אישור: `writing-plans.md` → משימות קטנות; ביצוע עם `executing-plans.md`.
6. אחרי ביצוע: `verification-before-claim.md` לפני «סיימתי».

## דגלים אדומים

| מחשבה | מציאות |
|---|---|
| «פשוט מדי לעיצוב» | עיצוב קצר ≠ בלי אישור |
| «Bounded כי אני מכיר את הסוג» | Bounded = זרימה קיימת בריפו, לא היכרות כללית |
| «הספייק עובד — נשאיר» | שמירת קוד = בקשה חדשה + סיווג מחדש |
| «כמעט סיימתי — לא צריך לשדרג» | מורכבות חדשה משדרגת מסלול מיד |
| «גריל ללקוח מספיק» | גריל פנייה ≠ אישור בנייה פנימית |
