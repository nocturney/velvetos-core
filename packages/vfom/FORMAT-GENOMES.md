# Velvet Format Genomes

Reusable story structures for Velvet Factory. These are mechanics, not scripts. Apply real studio evidence and Visual OS each time; never clone another creator's identity.

## `PROOF_UNDER_PRESSURE`

- 0-2s: action/tension/proof first.
- 2-6s: what problem or uncertainty is being tested.
- 6-14s: only the process needed to understand the proof.
- 14-22s: test/use/install/fit.
- 22-28s: verified result.
- 28-30s: short conclusion/question when useful.

Best for load, fit, durability or practical use where real proof exists.

## `FAIL_FIX_PROVE`

- failure or flawed result.
- one-line cause/context.
- changed model/material/process.
- new attempt.
- proof/result.

Best for iteration stories. Never stage or invent a failure.

## `VERSION_ONE_TO_FOUR`

- show final version or contrast immediately.
- rapidly compare meaningful iterations.
- isolate the change that mattered.
- final real-world proof.

Best when versions and evidence are actually available.

## `PROBLEM_TO_PART`

- irritating real problem first.
- printed part appears quickly.
- one or two process/details shots.
- installation/use proof.
- concise result.

Best for functional products that solve a visible problem.

## `MATERIAL_VS_MATERIAL`

- side-by-side subject/material reveal.
- one meaningful difference at a time.
- equal test conditions where evidence permits.
- verified conclusion, or explicitly inconclusive result.

Do not imply laboratory rigor or numerical superiority without evidence.

## `PROCESS_IN_THREE`

- result first.
- stage 1: model/prep.
- stage 2: print/process.
- stage 3: finish/use.
- return to final object.

Use only when proof footage is weak but the process itself is interesting.

## `TIMELAPSE_TO_RESULT`

- final result flash first.
- short timelapse, aggressively compressed.
- detail/macro.
- real use or pickup-ready state.

Avoid long printer timelapse with no payoff.

## `MYTH_REALITY`

- visible claim/question.
- real evidence immediately.
- concise explanation.
- result/qualification.

Use only with evidence-backed factual claims.

## `AUDIENCE_QUESTION_PROOF`

- question on screen.
- show the relevant object/constraint.
- answer with real demonstration.
- concise conclusion.

Use actual recurring questions when known; do not fabricate customer quotes.

## Selection rules

1. Prefer a genome that exposes the strongest real proof earliest.
2. Reject a genome that requires missing physical evidence unless a minimal `shotRequest` is acceptable.
3. Check novelty/fatigue before reuse. A genome may repeat, but first frame, proof mechanic, product, camera angle and pacing should not become formulaic.
4. Record the selected genome in the Creative Manifest.
