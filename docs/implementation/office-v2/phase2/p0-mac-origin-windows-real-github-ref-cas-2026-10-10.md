## Actual machines and why this design

Two original **physical** machines were used: `MacMiniOffice.local` (`192.168.0.217`) and **Chris Windows**. Windows has an independently inspected existing native GitHub CLI account with `repo` scope and reported GitHub `permissions.push=true`. A native Git `push --dry-run` of the exact scratch branch under the newly isolated Windows clone was authorized; **no new key/token was created, extracted, persisted, or installed**, and no Git credential helper was changed. Mac was verified able to **read** the canonical GitHub HEAD, but had **no verified native authenticated push credential**, consistent with the original #612 limitation. Direct Mac→Windows private-LAN TCP connectivity to a short-lived port failed by timeout; Windows→Mac outbound had previously been verified, so no Windows firewall rule was modified.

A disposable **read-only Mac request endpoint** (not a scheduler or new lease store) served six narrowly whitelisted JSON request fixtures under short-lived self-issued lab-only mTLS at `https://192.168.0.217:32683/v1/fixture/<phase>`. **Only** the Windows certificate CN `vf604-win-native-github-cas-sink` was authorized; no request offered a write endpoint. Windows's **one native Git writer** fetched each request with an exact TLS CA/client certificate, validated hardcoded target repo `nocturney/velvetos-core`, exact scratch ref `refs/heads/office-v2-lab-604-mac-origin-cas-20261010`, canonical base SHA `cc2cccb2770a79424741719795d552fa85d69a81`, exact action and expected SHA allowlist. It used Git's native **`push --force-with-lease=<ref>:<expected>`**, never an unconditional `--force`. The underlying **GitHub remote ref** (not a local mock) enforced the conditional update; Windows independently read back its effect after every push. Mac read back the remote ref with a separate native read-only Git client before subsequent requests and before cleanup.

Scratch commits were **synthetic no-content-change commits** all referencing the exact validated main tree and carrying a different clear LAB commit message. They were pushed **only to the unique temporary scratch branch**; no source files, protected PR branch or main ref were changed by this LAB.

## Critical *negative* architecture conclusion

**A conditional Git ref update is a REAL sink-native atomic CAS of that ref, but it does NOT authorize a stale worker relative to etcd.** If an etcd lease is revoked/expires while the target Git ref SHA remains unchanged, a stale worker with that still-current SHA could potentially win `--force-with-lease`. Git protects the object/version it knows, not an independent provider's unobserved lease generation. Likewise Git CAS does not protect filesystem writes, model calls or other systems. A safe #604/#612 design must ensure a separately authenticated *receiver-side* cutover or revocation marker updates the sink before new owner actions are admitted, with UNKNOWN/CAS conflicts reconciled before another worker proceeds; alternatively must demonstrate another proven single authoritative atomic protocol. **This LAB did not perform or claim such provider-to-Git integration.**

Do **not** merge this proof into a generic Fleet/Scheduler/provider contract as if it solved the cross-store TOCTOU or granted Mac native GitHub credentials. This was one Windows Git writer, with one Mac *request source*, not two different native Git writers. It was a historical, manually curated synthetic scratch-ref experiment, NOT a new model agent proposing or merging a protected code PR. Its sole production-adjacent value is the actual sink native compare-and-swap behavior and a bounded, cleaned-up way to call it from a physically different origin over mTLS.
