## Critical reliability and security limits

The etcd transaction, POSIX hardlink, and final receipt transaction occur in **three separate transactional domains/steps**. They are **not one global atomic commit**. If the receiver crashes/disconnects after intent but before filesystem creation, it retains `UNKNOWN_OUTCOME` and *must not blindly retry or move owner*. If it crashes after filesystem link but before the committed provider receipt, the on-disk file may exist while provider still says PENDING. A separate independent original-effect reconciliation is required. The observed four successful write cases and their duplicates **do not prove universal exactly-once execution under arbitrary faults**. The temporary Mac receiver ran under the normal Mac user; **OS users/processes with direct permission to its LAB folder were not isolated at a production filesystem ACL boundary**. There is still no native protected GitHub writer effect, no Mac native GitHub push credentials, no physical multi-writer Git race, no malicious node/CA theft protection or tested server-cert rotation, no multi-node etcd quorum/HA, no network partition/clock-skew injection, no autonomous model worker/PR/merge and no production authority. Client certs were ephemeral for this one LAB, not a reusable production security configuration.

This deliberately does **not** add a Fleet scheduler, universal effect gateway, long-running receiver, parallel source-of-truth or an Office production action. #604 should next choose the minimum ready-made placement/lease provider and define **receiver-native** effect fencing for Git or artifacts under authenticated writer identity, with a testable causal cutover and mandatory UNKNOWN reconciliation. #612 remains P0 PARTIAL until actual new physical-host coding workers produce distinct protected PRs under that authority.
