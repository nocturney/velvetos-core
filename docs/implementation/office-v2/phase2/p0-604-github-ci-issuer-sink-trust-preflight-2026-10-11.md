## The previously untested failure mode

An agent-authored PR can bring its own new green workflow and/or edit the scripts that a trusted existing workflow launches. A green check linked to the correct PR head is meaningful execution evidence, but is **not automatically an independent authorization policy that existed before the PR**. If a privileged sink accepts a worker-supplied `run_id`, status string or mutable Git SHA as a substitute for a trusted issuer, an unreviewed worker can potentially authorize itself. This matters **in addition to**, not instead of, the #670 actual expired-owner GitHub write acceptance and the credential-owner / Docker-daemon trust failures in #675/#688.

## Architecture consequence / actionable next implementation gate

1. **Trust the verification program before trusting its result:** a future promoted QA path must execute a previously reviewed runner+policy supplied from a trusted protected-base commit; load new PR source only as SHA-pinned data into a separate credential-free guest, never run the PR's modified verifier/workflow code with secrets. A status check alone, especially one introduced by its own PR, is not permission for the Git Sink. Keep protected author/reviewer and exact-head PR checks. GitHub's current [security guidance on `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) specifically warns against checking out and running untrusted PR head with an elevated token; this LAB does not add a `pull_request_target` workflow.
2. **Separate the OS credential principal for real:** a dedicated trusted sink principal must hold on-demand scoped GitHub App installation tokens (single repo, minimum needed permissions, <=1-hour expiry) or equally isolated credentials, with no access from Windows generated-code processes, Mac Qwen UID, PR Docker guests, or the Docker daemon that owns their mount namespace. GitHub's [GitHub App token documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app) describes bounded repository/permission scope and expiration. **No App was created, no token minted, no OS account or ACL modified in this work.** A GitHub App token is not intrinsically branch-scoped; the guarded sink still needs explicit repo/ref allowlists and branch rules.
3. **Use #604's sole authenticated lease / epoch authority and durable intent:** the sink independently re-reads provider generation/TTL and remote ref, records an authoritative durable `EFFECT_IN_FLIGHT` before any external Git effect, serializes and CASes only the exact allowed scratch ref, rereads both provider and GitHub after, and freezes uncertain, late, revoked, lost-ACK and process-still-alive outcomes as **UNKNOWN** with **NO BLIND RETRY**. No arbitrary worker JSON can mint a provider lease. The prior #670 live test proved that an expired owner still pushed when GitHub SHA had not moved; GitHub CAS alone cannot fence against the provider clock.
4. **Independently revalidate trust at runtime:** static snapshots, frozen hashes, private GitHub ruleset GETs, named CI run IDs or benign Docker negatives never establish sole token access or race-free multi-provider state. Before approving the actual sink, obtain a physically/OS-isolated credential principal and run live adversarial token/cross-host expiry tests against only a scratch namespace. An ordinary same-UID Mac key directory, Docker mount isolation under a privileged daemon, or Windows SYSTEM keychain under the same worker context are insufficient (prior #675/#688).

**Current verdict:** #604 remains **OPEN / RED** for true writer principal and provider/sink fencing. #612 remains **OPEN / PARTIAL**. This is new verified policy-ingress evidence, NOT proof of an autonomous two-host agent fleet, user-session Sandbox VM, production writer, general code safety, distributed exactly-once transactions or an installed orchestration system.
