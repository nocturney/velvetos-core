# Office 2.0 / #604 — Docker HOST daemon can initiate guest signer key use: expected SECURITY NEGATIVE

**Date: 2026-10-11. Status: real GitHub-hosted synthetic HOST-DAEMON KEY-USE NEGATIVE confirmed; Git Sink remains RED/not admitted.** This is a deliberately adversarial test using only disposable SYNTHETIC HMAC bytes on a GitHub-hosted ephemeral runner, NOT a real GitHub credential or a proposed new signing service.

## What is and is not isolated

[#686](https://github.com/nocturney/velvetos-core/pull/686) proved twice that two simultaneously running Docker guests sharing the same UID65534, but **separate mount namespaces**, did not expose a signer's fake tmpfs key to the worker guest. The current test isolates a further trust assumption: the **Docker daemon controller on the host** can request execution of an additional process *inside the same signer guest and its private mount namespace*, with the signer's own UID, whether or not a peer worker guest can see the private filesystem.

## Controlled HOST-privilege negative

Workflow `.github/workflows/office-p0-host-daemon-key-negative.yml` is PR-change-only, `permissions: {}`, `actions/checkout@v7 persist-credentials:false`, standard hosted Ubuntu24.04; no production secret, cloud IAM, model API or remote shell to a user's machine. It reuses the exact protected OCI digest `python@sha256:0a310eeecf4e1f5a0743f9a6520c90c88d089c903ca5fd283f501e3a805f5f89`.

The owned disposable signer container is created as UID65534 with read-only root/public fixture mount, network=none, CapDrop ALL, no-new-privileges and **signer-only private tmpfs `/sink`**. It generates a new **random synthetic** 32-byte HMAC key inside `/sink/signer-only.key` and emits only an HMAC for a fixed public synthetic message. The Python verifier checks actual Docker HostConfig and mount scope and waits until signer is live.

The host Docker controller (which is trusted to issue `docker exec` calls) then requests a **new process within the signer guest**, explicitly as the SAME UID65534. That controlled guest reference process reads only the synthetic key from its own namespace, calculates the HMAC of the original public message, and outputs only a JSON `uid`, `key_length` and `mac` (the secret key bytes NEVER leave the guest). The host verifies its HMAC equals the original live signer's HMAC, and that the signer remains live afterward. Result `PASS_EXPECTED_NEGATIVE_DAEMON_CAN_INVOKE_SYNTHETIC_SIGNER_KEY_USE` means **a controller of the Docker daemon can make the signer use the key**; it does not claim the host copied/exported the raw key, and emphatically does NOT mean the key is secure from Docker-host administration.

The first experimental [PR #687 run #38110417230](https://github.com/nocturney/velvetos-core/actions/runs/38110417230) failed closed when direct `docker cp ...:/sink/signer-only.key -` was denied. It produced no key material or false success and is preserved as historical negative capability evidence. **That path did NOT prove that the daemon could export the key.** The current revised test switches to daemon-requested container-local key use. A new [exact-head GitHub-hosted job #38110573435](https://github.com/nocturney/velvetos-core/actions/runs/38110573435) has now **SUCCEEDED**, returning `PASS_EXPECTED_NEGATIVE_DAEMON_CAN_INVOKE_SYNTHETIC_SIGNER_KEY_USE`: the daemon-initiated second process used the fake key while the original signer was live before and after, UID65534, exactly one read-only mount, signer-only tmpfs and the same immutable OCI digest. The emitted result confirmed `host_daemon_initiated_live_signer_key_use=true`, `raw_key_bytes_logged_or_exported=false`, `docker_cp_archive_test_succeeded=false` and `production_git_secret_custody_safe=false`. Thus this demonstrates signer **key-use authority from Docker host control**, not raw-key exfiltration. Protected Office full CI and merge/postmerge verification are separate acceptance gates and must remain pending until run readback.

Local pure `selftest` **11/11 PASS** on Mac, makes zero Docker calls/keys/model calls, and local `run` refuses before any container. Independent Windows byte-level static check, GitHub live test, protected CI and post-merge main verification remain separate requirements.

## Admission and limitations

Even if this expected host-daemon negative succeeds, it proves only **daemon controller capability in a disposable signer guest with a known test HMAC**. It does not demonstrate raw key exfiltration, arbitrary container escape, mTLS authority, remote GitHub write token custody, isolation from a compromised host, an independent signer across trust roots, stale-lease native GitHub push denial, durable `EFFECT_IN_FLIGHT` exactly-once reconciliation or production admission. A different separately controlled trust root for the real signer is still needed before trusting unknown generated agents with write effects. Existing six workflow `contents:write` domains are unchanged; they must not be silently disabled.

**No real credential, certificate, user file, customer/business record, Instagram, CAD, printer or operating-system security setting is opened or modified.** No new daemon, paid model, Codex, scheduler or production authority is added. #604 remains RED, #612 PARTIAL; local unconfined Diverse Worker from #683 remains fail-closed.
