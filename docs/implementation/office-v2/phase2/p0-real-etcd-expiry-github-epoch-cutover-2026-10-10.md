## Hard security/reliability boundary: the unresolved race is real

GitHub's `--force-with-lease` atomically protects only the **Git ref's SHA**. The old worker in this LAB *really did* write after its etcd TTL expired: GitHub had no provider-epoch awareness. Advancing the Git ref to a new generation marker **before activating a new provider owner** prevented **the tested old request whose expected SHA was from before that marker**; it does not make etcd and GitHub one transactional domain. This protocol still has a vulnerable race between **lease expiry and marker cutover** (proven by the intentionally unsafe push), and between provider preflight and Git write/timeout. A malicious Windows process holding the sole Git credentials can bypass the tested client, and a previous owner with a still-current SHA can win if the trusted sink fails to freeze operations during provider expiry/handoff. For full safety the credential-owning sink must be the exclusive, authenticated, serialized executor, fail closed on unknown liveness/freshness, freeze on expiry/partition until sink epoch marker advances and is independently reconciled, and precisely define conditional owner admission in **one existing ready-made canonical provider**, not a second scheduler.

No real provider quorum/HA/clock skew/mid-push partition fault, revocation during push, customer/CAD/social/printer effect, native Mac GitHub writer credential, autonomous model worker/QA protected PR chain, production OS ACL, production cert-rotation lifecycle or universal exactly-once Git effect was demonstrated. The test was a **short-lived single-node etcd plus mTLS fixture** with a single native Windows writer and manual human-controlled experiment phases, not a production coordinator.
